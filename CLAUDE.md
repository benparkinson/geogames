# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Geogames: geography quiz games. The backend is Spring Boot 4 / Java 25 / Maven, at the repo root. The frontend is Next.js 16 / React 19 / TypeScript, in `client/`. It uses TanStack Query (`@tanstack/react-query`), react-bootstrap and react-leaflet.

## Commands

Backend (repo root; use `./mvnw` or `mvnw.cmd` if `mvn` isn't installed):
- Full build (also builds the frontend and bundles it into the jar): `mvn clean install` (add `-DskipTests` to skip tests)
- Run the packaged app: `java -jar target/geogames-0.0.1-SNAPSHOT.jar`. It serves on port 8080.
- Run the backend in dev: run the main method of `GeogamesApplication` (for example from IntelliJ), or use `mvn spring-boot:run`
- Tests: `mvn test`. Run a single test with `mvn test -Dtest=TripointFinderTest` or `-Dtest=TripointFinderTest#methodName`. `mvn test` and `mvn install` also run the frontend Vitest suite (a `frontend-maven-plugin` execution in the `test` phase), and `-DskipTests` skips both. A plain `mvn verify` still runs everything (frontend lint, build and Vitest, the Java unit tests, the integration tests, the JaCoCo gate and `spotless:check`).
- **Unit and integration tests.** Test classes whose name ends in `IT` (`GameApiIT`, `ApiContractIT`, `HttpServerIT`, `ApplicationContextIT`, `ProcessedDataIT`) are integration tests, run by Failsafe in the `verify` phase (`mvn test` does not run them). Every other test class is a unit test for Surefire. The JaCoCo coverage gate counts the unit tests only. Switches, all default to `false`, that let one command run just a part: `-DskipUnitTests` (Surefire and the frontend `npm test`), `-DskipITs` (Failsafe), `-Dskip.lint` (`npm run lint`) and `-Dskip.frontend` (Node, `npm ci`, lint, the Next build and Vitest; a bundled jar then needs `client/out` from an earlier build, and `HttpServerIT` is skipped without it). `-DskipTests` still skips everything. For example, only the Java unit tests: `mvn verify -Dskip.frontend -DskipITs -Dspotless.check.skip=true`; only the frontend build and the ITs: `mvn verify -DskipUnitTests -Dskip.lint -Djacoco.skip=true -Dspotless.check.skip=true`. The old `-Dskip.npm -Dskip.installnodenpm` still works but does not skip lint; prefer `-Dskip.frontend`.
- **Contract test.** `client/src/test/api-shapes.json` holds the shape of every JSON response the frontend reads (per game type, plus `/api/countries`, `/api/rivers`, `/api/lakes` and `POST /api/games`). `ApiContractIT` fails when the backend's responses stop matching it; regenerate with `mvn verify -Dcontract.update=true -Dit.test=ApiContractIT` (add `-Dskip.frontend -DskipUnitTests -Djacoco.skip=true -Dspotless.check.skip=true` to run only that) and commit the file. The frontend's `client/src/api/contract.test.ts` then fails until its fixtures (`client/src/test/fixtures.ts`) match the new shapes, or the new backend fields are listed in its `IGNORED_BACKEND_FIELDS` with a reason. The shape format is in `JsonShape.java` and `client/src/test/shape.ts`; keep them the same.
- **Browser tests** (`e2e/`, Playwright with Chromium, its own `package.json`). They play every game in a real browser against the jar, with no internet: all non-local requests are blocked, and a test fails if the page called `onrender.com`. Build the jar with the API override, then run them: `NEXT_PUBLIC_API_URL=http://localhost:8080 mvn -B -DskipTests package`, then `cd e2e && npm ci && npx playwright install chromium && npx playwright test` (Playwright starts the jar itself; see `e2e/README.md`). `deep-link.spec.ts` is marked `test.fail()` for a known bug (reloading `/games/{id}` served by the jar is a 404); when the bug is fixed that test starts failing, so remove the marker.
- Backend test conventions: JUnit 5, AssertJ and Mockito. Boot 4 moved the test slices out of `spring-boot-test-autoconfigure`, so `@WebMvcTest` / `@AutoConfigureMockMvc` come from `spring-boot-starter-webmvc-test` (package `org.springframework.boot.webmvc.test.autoconfigure`) and `@DataJpaTest` from `spring-boot-starter-data-jpa-test`. Use `@MockitoBean` (`org.springframework.test.context.bean.override.mockito`), not `@MockBean`. No test may hit the network. `TripointComputer` is tested against the hand-written HTML in `src/test/resources/fixtures/`.
- Format Java (google-java-format via Spotless): `mvn spotless:apply`. Check formatting with `mvn spotless:check`.

Frontend (`client/`):
- Dev server with hot reload on port 3000: `npm run dev`. It calls the backend at `http://localhost:8080`.
- Type-check: `npm run typecheck` (`tsc --noEmit`; CI runs it with lint).
- Lint: `npm run lint` (zero warnings allowed). `mvn verify` runs it, and also `spotless:check`, so a PR fails the required `test` check if either fails. TypeScript is pinned to 6.0 (`~6.0.3`) because typescript-eslint doesn't support TS 7 yet (typescript-eslint#10940); Dependabot ignores major TypeScript bumps. Drop the pin and the `ignore` entry once it does.
- Lint rules check: `npm run lint:rules` lints `client/lint-probe/probe.tsx`, which breaks one rule from each ESLint plugin, and fails unless every rule in `scripts/check-lint-rules.mjs` fires. This catches a plugin that silently stops reporting after an ESLint upgrade (several declare peer `eslint` ≤ 9). `npm run lint` and `tsc` ignore the probe folder. When adding a plugin, add a violation and its rule id to both files.
- Version check: `bash scripts/check-versions.sh` (repo root) fails unless the versions agree: `<java.version>` in `pom.xml`, every `setup-java` `java-version` in `.github/workflows` and both `temurin` tags in the `Dockerfile`; `<nodeVersion>` in `pom.xml` and `client/.nvmrc`; and the `@types/node` major in `client/` and `e2e/` with the Node major. A Java or Node upgrade changes all of them together. Dependabot ignores `@types/node` majors, and it files a JDK change in a Docker tag as minor, so this check is what makes those PRs fail.
- Production static export: `npm run build`. This runs `next build` (with `output: "export"` in `next.config.mjs`) and writes to `client/out/`. Before that (and before `npm run dev`) `scripts/third-party-licenses.mjs` writes the licence text of every production npm package to `public/third-party-licenses.txt` (git-ignored), which the home page footer links to: the minified bundle keeps no licence comments, and MIT/BSD/Hippocratic (react-leaflet) licences need the notice to ship with the code.
- **Credits.** The home page footer credits Natural Earth (all geometry), Wikidata (names), Wikipedia (the tripoint list, CC BY-SA), Esri (satellite imagery) and the Flaticon icon authors. Esri's terms also need its credit on the map itself: always draw satellite imagery with `map/SatelliteTiles` (which sets the `attribution`), never a bare `TileLayer`. A new data source or tile layer needs a credit added to the footer.
- Tests (Vitest + React Testing Library + jsdom): `npm test` (single run), `npm run test:watch`, `npm run coverage` (v8; only the `*MapWrapper.tsx` files are excluded). Tests are colocated with their source as `*.test.ts(x)` under `client/src`, and shared helpers (fixtures, a `fetch` router, a query-client wrapper) live in `client/src/test/`. Never put test files under `client/pages/`, because Next would treat them as routes. Test files are type-checked by `next build`, so import `describe`/`it`/`expect`/`vi` from `vitest` explicitly. Never render real Leaflet maps: mock the `*MapWrapper` modules in tests of the games, and test the `*Map.tsx` components themselves with `vi.mock("react-leaflet", async () => await import("../../test/leafletMock"))`, which draws each layer as a `<div>` so a test can check what is shown while playing and after the round (`drawnLayers()`, `drawnTileUrls()`, `drawnMarkers()`). Testing Library only detects Jest's fake timers, so with `vi.useFakeTimers()` use `fireEvent` instead of `userEvent`. Components use TanStack Query through the provider in `pages/_app.tsx`, so tests wrap them in a `QueryClientProvider` (`renderWithClient` in `client/src/test/render.tsx`).
- Use the Node that Maven installed (`target/node`, v24) for npm commands. The system Node may be older than Next 16 supports.

## Git workflow

`main` is protected: changes must go through a pull request and the required `test` status check, so pushes to `main` are rejected. Never commit to or push `main`. Create a feature branch first, push that, and open a PR.

## CI

`.github/workflows/ci.yml` runs one job per kind of failure, so a red check names what broke: `lint-backend` (Spotless), `lint-frontend` (ESLint, `npm run lint:rules`, `tsc` for `client/` and `e2e/`, and `scripts/check-versions.sh`), `unit-backend` (Surefire and the JaCoCo gate, no Node), `unit-frontend` (Vitest and its coverage thresholds), `build` (the bundled jar, built with `NEXT_PUBLIC_API_URL=http://localhost:8080`), `integration` (the `*IT` classes, including the contract and data checks, against the built frontend), `contract-frontend` (the frontend half of the contract), `e2e` (Playwright against the jar), `docker` (builds the production `Dockerfile` image, runs it with `--memory=512m` and calls the API) and `data` (regenerates the processed data and compares it with the committed files). `test` is the aggregate: it needs all of them and fails unless each succeeded, and it is the one required status check on `main`, so keep its id and name. Pull requests cancel superseded runs. `smoke-production.yml` is the only workflow that touches the network (it calls the deployed services, on demand and daily) and never runs on a PR. Nothing run on a PR may reach the internet.

## Architecture

**Build coupling.** The Maven `frontend-maven-plugin` installs Node 24 into `target/`, then runs `npm ci` and `npm run build` in `client/`. `maven-antrun-plugin` copies `client/out` into `target/classes/public`, so Spring serves the static site and the API from the same jar. The `Dockerfile` does the same build in two stages.

**Environment switching.** `client/src/api/gateway.ts` (`serverEndpoint()`) picks the backend URL from `NODE_ENV`: production uses `https://geogames-web-service.onrender.com`, anything else uses `localhost:8080`. If `NEXT_PUBLIC_API_URL` is set (and not empty) at build time, it wins over both: the browser tests build the bundled site with `NEXT_PUBLIC_API_URL=http://localhost:8080` so the jar talks to itself instead of production. Never set it for the Render build. The allowed CORS origins are the `geogames.cors.allowed-origins` property in `application.properties` (comma-separated), applied to `/api/**` by `config/WebConfig`. Update it if the hosting changes.

**Game flow / API** (`GameController` → `GameService`):
- `POST /api/games` with `{gameType, numberOfRounds}` (1–10). `gameType` is `TRIPOINT`, `RIVERS_BY_SHAPE`, `RIVERS_ON_MAP`, `RIVERS_BY_ENDS`, `RIVERS_BY_COUNTRIES`, `COUNTRIES_BY_NEIGHBOURS`, `COUNTRIES_BY_COASTLINE`, `COUNTRIES_BY_LAND_BORDERS`, `LAKES_BY_SHAPE`, or `RANDOM` (a mix of every game type). Invalid input (rounds outside 1–10, an unknown `gameType`, more rounds than there is data for, or answering with `UNANSWERED`) returns 400 with a `ProblemDetail` JSON body (`controllers/ApiExceptionHandler`).
- `GET /api/countries` returns `[{name, additionalNames}]` for every processed country. It is used for Tripoint autocomplete and guess validation, and is cached.
- `GET /api/rivers` and `GET /api/lakes` return the same shape for every river or lake: for autocomplete and spell checking, cached.
- `GET /api/games/{id}/rounds/{round}` returns a `GameRound`: the game type, `jsonBlob`, the total round count, the answer state, `hintsUsed`, `points` (this round's points) and the overall `GameResult` (`score` is the sum of round points out of `maxScore`, plus `roundsCorrect`, `perfectRounds`, and per-round `roundPoints` / `roundHintsUsed`).
- `POST /api/games/{id}/rounds/{round}/answers` with `{answerState, hintsUsed, wrongGuesses}` (`CORRECT` / `GAVE_UP` / `OUT_OF_GUESSES`; a missing `hintsUsed` counts as 0, and more than the type's `hintCount` is a 400). A missing `wrongGuesses` is stored as unknown (`null`), not 0, so an old client can be told apart from a round with no wrong guesses. It is a 400 when it is negative, more than the type's `guessLimit`, not equal to `guessLimit` for `OUT_OF_GUESSES`, or equal to `guessLimit` for `CORRECT` / `GAVE_UP`. The field is stored on the round but not returned, so the response contract is unchanged. Repeating the identical answer is a no-op; any other answer to an answered round is a 409.
- Games are stored with JPA in an **in-memory H2** database (`application.properties`), so they are lost on restart, and `GameCleanupService` also deletes each game `geogames.games.max-age` (24 h) after it is created. Each `GameRoundEntity` stores its round data as a serialized JSON string (`jsonBlob`, a `GameData` implementation such as `Tripoint` or `RiverRound`). The frontend `JSON.parse`s it.
- **The client checks answers, not the server.** The frontend compares guesses against the data in `jsonBlob`, including `additionalNames` aliases normalised by `stringHelper.normaliseString`, and only reports the final `AnswerState` to the server, with `hintsUsed` and `wrongGuessCount` (the guesses recorded with `answer === null`, so only those that use up the guess limit: empty, duplicate and unknown guesses and correct guesses don't count). The matching lives in `client/src/games/common/answers.ts` (`matchAnswer`) and the guess rules (duplicates, aliases, unknown names, hints) in the pure `guessReducer.ts` next to it. `guessReducer` also enforces `guessLimit` (only wrong guesses count) and can finish a round as `OUT_OF_GUESSES`; `GuessState.gaveUp` means "the answers are revealed" and is true both for giving up and for running out of guesses.

**Game types.** `model/GameType` is a Java **enum** with an `answerCount` (TRIPOINT=3, and 1 for every other type) **a `hintCount`** (how many hints the client offers) **and a `guessLimit`** (how many wrong guesses a round allows, at least 1; running out ends the round as `OUT_OF_GUESSES`). The client reads both from the API. It is persisted with `@Enumerated(EnumType.STRING)` and sent to clients as `api/GameTypeResponse` (`{name, answerCount, hintCount, guessLimit}`), so the JSON shape doesn't depend on the enum. `RANDOM` is a request-only value, parsed by `service/GameSelection`, and is not a `GameType`. Adding a game type takes changes in these places:
1. A constant in `GameType`.
2. A `GameData` record in `model/` (its `gameType()` returns the constant, and `subjectId()` says what the round is about) and whatever loader services it needs. Skip this if the game can reuse an existing record, as the river games do.
3. A bean that implements `service/RoundGenerator` for the new type: a `@Service`, or a `@Bean` in a `@Configuration` when several types share one class. `GameService` picks up every generator bean by type, with no edits to the service, and `RANDOM` mixes every registered type. Startup fails with an `IllegalStateException` if a `GameType` has no generator, or has two. Generators take the shared `java.util.Random` bean (`config/RandomConfig`) and pick with `helper/RandomPicker`, so tests can pass a seeded `Random`. `generate(count, excludedSubjects)` must not return a round whose `subjectId` is excluded: `GameService` collects the subject ids already used in a `RANDOM` game and passes them to the next generator, so a mixed game never asks about the same tripoint or river twice (a river by shape and the same river on the map).
4. Frontend: create `client/src/games/<name>/` with a module built by `defineGame` (its fields are described in `games/types.ts`: the backend `type`, titles, description, icon, component and `answerNames`), a component (usually built on the generic `games/common/MapGame`), and a `*Map.tsx` + `*MapWrapper.tsx` pair that takes `MapProps<T>`. Then add the module to `GAME_MODULES` in `games/registry.ts`, whose order is the home page order. Set `extraDifficult: true` on the module to show it in the home page's "Extra difficult" section, after Mixed (River Shapes and Lake Shapes do this). Nothing in `games/common/`, `GameRoundPage`, `GameSummary` or `HomePage` needs to change. `MapGame` takes `blankMap` (a grey map while playing) and `mapCaption` (text over the map while playing) separately. The component gives `MapGame` its answers as `AnswerCandidate[]` (a name plus aliases), and matching (aliases, duplicates) is handled centrally. The component supplies `hints` content for `round.hintCount` hints (the count comes from the backend `GameType.hintCount`, so the component doesn't set its own), and `MapGame` reports `{answerState, hintsUsed, wrongGuesses}`. Scoring lives in `games/common/scoring.ts` and needs no per-game code.

**Scoring.** A correct round is worth 100 points; hints share a 50-point penalty equally between the type's `hintCount` hints, so answering after all hints scores 50; a revealed round (`GAVE_UP`) scores 0, and wrong guesses cost nothing until the type's `guessLimit` is reached, which ends the round as `OUT_OF_GUESSES` with 0 points. The client reports `hintsUsed` with the answer and the server computes the points when needed (they are never stored). The formula lives in `model/Scoring` and `client/src/games/common/scoring.ts`, which must agree (both tests hold the same table). A new game type only chooses its `hintCount` and `guessLimit`.

**The river family.** Four game types share the 50 rivers in `processed/rivers` (balanced across continents by `RIVER_QUOTAS` in `RiverLoaderMain`): `RIVERS_BY_SHAPE` (the line on a blank map), `RIVERS_ON_MAP` (the line on satellite imagery, limited zoom, no panning), `RIVERS_BY_ENDS` (a flag at the source and the mouth) and `RIVERS_BY_COUNTRIES` (the simplified outlines, from `processed/country-shapes`, of the countries it flows through; only rivers through three or more). One `model/River` is the file format, and `model/RiverRound` (`gameType`, `river`, `countries`) wraps it as round data. `service/RiverRoundGenerator` is one class, registered as four beans in `config/RiverGamesConfig` with an eligibility filter and a function that attaches countries. On the frontend, `games/rivers/RiverGame.tsx`'s `makeRiverGame(config)` builds each variant's component from a map, a prompt, caption and hints, with shared layers in `RiverLayers.tsx` and hint builders in `riverHints.ts`. `map/LockedView` fits a map to some bounds, limits the zoom and turns off panning until the round ends. To remove a variant, delete its `GameType` constant, its `@Bean`, its module, its registry entry and its map pair.

**Lake Shapes.** `LAKES_BY_SHAPE` (`answerCount` 1, `hintCount` 3, `guessLimit` 5) shows a lake's polygon on a blank map with a scale bar, and the satellite map once the round ends (solved, given up or out of guesses). `model/Lake` is the file format in `processed/lakes` and `model/LakeRound` (`gameType`, `lake`) the round data; its subject id is `lake:<QID>`. `service/LakeLoaderService` reads the files (cached as `lakes`, plus `lakeNames` for `GET /api/lakes`) and `service/LakeRoundGenerator` is a plain `@Service`. On the frontend, `games/lakes/` holds the module (`index.ts`), `LakeGame.tsx`, the `LakeShapesMap` pair, `lakeHints.ts` (continent, countries on the shore, first letter) and uses `useGuessList("lakes")`.

**The country-shape family.** Three game types draw on the simplified shapes in `processed/country-shapes`: `COUNTRIES_BY_NEIGHBOURS` ("Country Gaps": the neighbours' filled outlines, the country is the gap), `COUNTRIES_BY_COASTLINE` (only the coast as lines) and `COUNTRIES_BY_LAND_BORDERS` (only the land borders as lines). `model/CountryShape` is the file format and `model/CountryShapeRound` (`gameType`, `country`, `neighbours` as `CountryOutline`s) the round data; its subject id is `country:<name>`, shared by all three games. `service/CountryShapeRoundGenerator` is one class, registered as three beans in `config/CountryGamesConfig`, with the eligibility thresholds (and the reason for each) in `helper/CountryShapeEligibility`. The games use `useGuessList("countries")` and `isKnownGuess`. On the frontend, `games/countries/CountryShapeGame.tsx`'s `makeCountryShapeGame(variant)` builds each component from a map, a prompt, a caption and hints, with shared layers in `CountryLayers.tsx` (`FocusFit` fits the largest part, so Russia, Fiji and overseas territories don't zoom out to the world) and hint builders in `countryHints.ts` plus the generic `games/common/hints.ts`. Removing a variant works as for rivers.

**Backend structure** (`com.parkinson.benjamin.geogames`). `api/` holds the HTTP request and response records, `model/` the domain types, `dao/` the JPA entities and repository, `service/` the game logic, the round generators and the data loaders, and `config/` the Spring configuration (caching, CORS, `Random`, logging). Loader services read classpath JSON through `service/JsonResourceReader`, and the offline `loaders/` programs share the Jackson settings in `helper/GeoJson`. Data that fails to load is an `UncheckedIOException` (a packaging bug), not a checked exception. `GameService` methods are `@Transactional` and `spring.jpa.open-in-view` is off, so the lazy `rounds` collection must be read inside the service.

**Leaflet and SSR.** Leaflet can't render on the server. Each map has a `*MapWrapper.tsx` that is just a `dynamic(() => import("./X"), { ssr: false, ... })` call (keep the `import(...)` literally in that file), and the real `*Map.tsx` takes `MapProps<T>` (`data`, `gameOver`, `gaveUp`, `hintsUsed`). Follow this pattern for new maps.

**Frontend structure** (`client/src`). `api/` owns fetching (`fetchJson`), query keys, hooks and the one `JSON.parse` of `jsonBlob`, and components never call `fetch`. `games/common/` is the game-agnostic shell (round page, summary, `MapGame`, answer matching and guess reducer). Each `games/<name>/` folder holds one game: its module, component, model types and maps. `games/registry.ts` is the only list of games. `map/` holds the shared Leaflet helpers. `useGuessList(kind)` (in `games/common/`) gives the autocomplete and spell check for countries, rivers and lakes; a game whose answers come from a fixed list should use it. The `QueryClientProvider` lives in `pages/_app.tsx`.

**Geo data pipeline**:
- `geodata/countries/` (repo root, **not** in the jar) holds the raw sources: `countries.geo.json` (Natural Earth) `additionalNames.json` (aliases) and `excludedNames.json` (non-country features such as bases and reefs to skip). `geodata/rivers/` (also not in the jar) holds the river sources: `naturalearth/ne_10m_rivers_lake_centerlines_scale_rank.geojson` (Natural Earth, public domain; the plain `lake_centerlines` file has no Wikidata IDs, this one does; it is the only source of river geometry), `wikidata.json` (Wikidata labels, aliases, sitelinks and continents per QID, committed) and `overrides.json` (hand-written, keyed by QID: `exclude`, `name`, `continent`, `aliases`, `addAliases`, `removeAliases`, `mainPieceOnly` (drop lines detached from the river's main piece, for a far-off stretch Natural Earth tags with the same QID, such as the Congo's upper Lualaba), `reverseFlow`, `source`, `mouth`; overrides only correct data and can't supply geometry: rivers are ranked by Wikipedia sitelinks whether or not they have an override, and the top of each continent is taken up to `RIVER_QUOTAS` in `RiverLoaderMain`).
- `geodata/lakes/` (also not in the jar) holds the lake sources: `naturalearth/ne_10m_lakes.geojson` (Natural Earth, public domain; the plain file, not the `_europe` / `_north_america` / `_historic` / `_pluvial` variants), `wikidata.json` (from `WikidataMain`, committed) and `overrides.json` (hand-written, keyed by QID: `exclude`, `name`, `continent`, `aliases`, `addAliases`, `removeAliases`, `countries`; `countries` replaces the located countries outright). Lakes are ranked by Wikipedia sitelinks, with the top of each continent taken up to `LAKE_QUOTAS` in `LakeLoaderMain`.
- `src/main/resources/processed/` holds files generated offline by standalone `main` programs, not part of the Spring app:
  - `loaders/countries/CountryLoaderMain <countries.geo.json> <additionalNames.json> <excludedNames.json> <outDir>` clears `*.json` in `outDir`, then writes `processed/countries/*.json` (one `Country` per file). Editing `additionalNames.json` or `excludedNames.json` means re-running this.
  - `loaders/countries/CountryShapeMain <processedCountriesDir> <outDir>` reads `processed/countries` and writes `processed/country-shapes/*.json` (one `CountryShape` per country, Antarctica left out): simplified `outline`, `coast` and `landBorders` lines, `neighbours` and a `focus` box. Coast and borders come from which edges two countries share (`CountryShapeBuilder`; shared borders are simplified identically on both sides so no gaps open). **Editing `additionalNames.json` or `excludedNames.json` means re-running `CountryLoaderMain` and then `CountryShapeMain`**, or `ProcessedDataIT` fails.
  - `loaders/tripoint/TripointLoaderMain <processedCountriesDir> <outFile>` scrapes Wikipedia's list of tripoints and writes the single file `processed/tripoints.json`, an array of `{coordinate, countryNames}`. Each Wikipedia coordinate is snapped by `TripointSnapper` to the vertex where the three countries' borders meet. A tripoint with no such vertex within 30 km is dropped. The tripoint count comes from the file, so there's nothing to update by hand.
  - `loaders/features/WikidataMain <naturalEarth.geojson> <outFile wikidata.json>` fetches the Wikidata facts for every QID in a Natural Earth file. **It is the only feature program that uses the network.** Run it once and commit `wikidata.json`. `loaders/features` is shared by every Natural Earth + Wikidata feature type (reader, Wikidata fetch, continents, aliases, fame-ranked selection with continent quotas, simplification, country location); `loaders/rivers` holds only what is about rivers.
  - `loaders/rivers/RiverLoaderMain <naturalEarth.geojson> <wikidata.json> <overrides.json> <countriesDir> <outDir>` is offline and deterministic. It also works out each river's `source` and `mouth` (`RiverEnds`: the two points furthest apart along the joined lines, with the flow direction voted from how the lines were digitised; `reverseFlow` or explicit `source`/`mouth` overrides fix the rivers it gets wrong) and the `countries` it flows through (`CountryLocator`, from `processed/countries`). It clears `*.json` in `outDir`, simplifies the geometry (Douglas-Peucker, at most 600 points per river) and writes `processed/rivers/<slug>-<QID>.json`, one `River` per file. It prints a summary, including famous rivers skipped for lack of a continent. Editing `overrides.json` means re-running this (no need to refetch Wikidata).
  - `loaders/lakes/LakeLoaderMain <naturalEarth.geojson> <wikidata.json> <overrides.json> <countriesDir> <outDir>` is offline and deterministic. It assembles lake candidates (`LakeAssembler`: at least 100 km² unless an override names the lake; `LakeGeometry` simplifies at most 800 points, dropping islands under 1% of their lake and fragments under 2% of the main body), picks the top of each continent, locates the countries on the shore (`CountryLocator.locateRings`, at least 5 km), clears `*.json` in `outDir` and writes `processed/lakes/<slug>-<QID>.json`, one `Lake` per file. It prints a summary including famous lakes skipped for lack of a continent and lakes with no countries. Editing `overrides.json` means re-running this (no need to refetch Wikidata).
- **Checking the data is current.** `bash scripts/check-processed-data.sh` (needs `JAVA_HOME`; this is what the CI `data` job runs) runs the `regenerate-data` Maven profile, which re-runs `CountryLoaderMain`, `CountryShapeMain`, `RiverLoaderMain` and `LakeLoaderMain` into `target/regen/`, then diffs each output directory against `src/main/resources/processed/`. It fails and lists the files when `geodata/` or a loader changed and the processed data was not regenerated. It skips `TripointLoaderMain` and `WikidataMain` because they use the network. `.gitattributes` keeps `processed/**/*.json` as LF so the diff is exact on every OS.
- At runtime `TripointFinderService` picks random definitions from `tripoints.json` and builds each country with `CountryShapeService.loadShape(name).toCountry()`, so the `jsonBlob` sent to the frontend carries the simplified `processed/country-shapes` outline (in the usual `Country` shape), not the full-resolution geometry of `processed/countries`.
- Rivers are read at runtime from `processed/rivers/*.json` by classpath glob and cached (`@Cacheable("rivers")`).
