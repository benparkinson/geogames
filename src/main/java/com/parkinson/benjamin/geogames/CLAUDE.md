# Backend

Spring Boot 4, Java 25. The root `CLAUDE.md` has the commands, the API overview and the scoring rules.

## Conventions

- Loader services read classpath JSON through `service/JsonResourceReader`, and the offline `loaders/` programs share the Jackson settings in `helper/GeoJson`. Data that fails to load is an `UncheckedIOException` (a packaging bug), not a checked exception.
- `GameService` methods are `@Transactional` and `spring.jpa.open-in-view` is off, so the lazy `rounds` collection must be read inside the service. Keep every transaction on `GameService`'s public methods: `GameController.retryOnConflict` relies on the transaction having ended when it catches an optimistic-lock conflict. The rest of the logic is in `RoundRules` (the guess, hint and answer rules: they change a round and never save), `RoundGenerators` (the generator for each type, the start-up checks, mixed games and rebuilds) and `GameResults` (points and the overall result). `DailyGameController` serves `POST /api/daily-games`.
- Coordinates read from JSON are `Position`s: an immutable `List<Double>` of two `double` fields (`model/geojson`, read by `CoordinatesDeserializer`, written by `PositionSerializer`), about a third of the heap of an `ArrayList` of two `Double`s, and the app holds hundreds of thousands of points. Only an array of exactly two floats becomes a `Position`; anything else stays a plain list. Code that builds geometry by hand may still use plain lists, and a loader must copy a position (`new ArrayList<>(position)`) before changing it.
- `config/` holds caching, CORS (`WebConfig`, applied to `/api/**`), `Random`, logging and the stats executor.

## Tests

JUnit 5, AssertJ and Mockito. Boot 4 moved the test slices out of `spring-boot-test-autoconfigure`, so `@WebMvcTest` / `@AutoConfigureMockMvc` come from `spring-boot-starter-webmvc-test` (package `org.springframework.boot.webmvc.test.autoconfigure`) and `@DataJpaTest` from `spring-boot-starter-data-jpa-test`. Use `@MockitoBean` (`org.springframework.test.context.bean.override.mockito`), not `@MockBean`. No test may hit the network. `TripointComputer` is tested against the hand-written HTML in `src/test/resources/fixtures/`. Run them with `bash scripts/check-java.sh` (unit) and `bash scripts/check-it.sh` (`*IT`). Code that runs off the request thread (`@Scheduled`, the statistics writer) needs an `*IT` without a test transaction (see `GameCleanupIT`), because a unit test's or `@DataJpaTest`'s transaction hides a missing one.

Build games with `TestFixtures` (`game(...)` for an entity, `createGame(mockMvc, ...)` in integration tests) unless the test is about a game's settings or the request itself. Then a new setting changes one class, not every test. In a test class with many calls to a service method, wrap the arguments the tests don't care about in a private helper.

## API rules

- Invalid input (rounds outside 1–10, an unknown `gameType`, more rounds than there is data for, or answering with `UNANSWERED`) is a 400 with a `ProblemDetail` body (`controllers/ApiExceptionHandler`).
- A malformed game id (including an old numeric one) is a 404, the same as an unknown game.
- Answers: a missing `hintsUsed` counts as 0, and more than the game's effective `hintCount` (`GameType.hintCount(Difficulty)`) is a 400. A missing `wrongGuesses` is stored as unknown (`null`), not 0, so an old client can be told apart from a round with no wrong guesses. `wrongGuesses` is a 400 when it is negative, more than the game's effective `guessLimit` (`GameType.guessLimit(Difficulty)`: doubled in Easy), not equal to it for `OUT_OF_GUESSES`, or equal to it for `CORRECT` / `GAVE_UP`. It is stored on the round but not returned, so the response contract is unchanged. A missing `answersFound` is unknown; otherwise it is a 400 when it is outside `0..answerCount`, not `answerCount` for `CORRECT`, or `answerCount` for `GAVE_UP` / `OUT_OF_GUESSES`. `GameService.answer` stores `answerCount` for `CORRECT`, and otherwise the larger of the reported count and the correct guesses recorded (below `answerCount`), or `NULL` if the client said nothing and none was recorded; `Scoring.roundPoints` turns it into the partial points of a revealed round, and `RoundAnswered` carries it so the stats `points` match the game. Repeating the identical answer (the same `answersFound` too) is a no-op; any other answer to an answered round is a 409. Two answers to one round at the same moment behave as if one came after the other: the round has a version (optimistic locking), and the controller retries once after a conflict.
- First guess (`GameResults.isFirstGuess`, returned as `roundFirstGuess` / `firstGuessRounds` in `GameResult`): the round is `CORRECT`, the effective `hintsUsed` is 0, the reported `wrongGuesses` is 0 (never `null`) and no stored guess has `correct == false`. It is a label only: scoring is unchanged.
- Guesses (`POST .../guesses`, `GameService.recordGuess`, rules in `RoundRules.addGuess`): a guess on an answered round is a 409. A null, blank or over-255-character guess, a name that is not in the round type's list (`KnownPlaceNames`; the text is never stored or logged), a missing `correct`, more wrong guesses than the game's effective `guessLimit` and more correct ones than `answerCount` are 400s. A guess with the same normalised name as a stored one changes nothing (a retried request is harmless). The server doesn't check `correct` and publishes no stats event. `submitAnswer` doesn't compare `wrongGuesses` with the stored guesses, so a guess request lost on the network can't block an answer. The controller retries a lost optimistic-lock race once, as for answers.
- Hints (`POST .../hints`, `GameService.recordHint`, rules in `RoundRules.addHint`): a hint on an answered round is a 409. A hint that is already recorded is a no-op (the first `guessesBefore` wins), a skipped hint, one at or past the game's effective `hintCount` and a negative `guessesBefore` are 400s, a missing field is a 400. A `guessesBefore` above the stored guess count is clamped to it, not rejected, because a lost guess request would otherwise turn a real hint into an error. No stats event. When answering, the stored hints are the larger of the reported `hintsUsed` (a missing one is 0) and the hints recorded, worked out before the repeat check so a retry is still a no-op; the stats event and the points use it too.
- Answering a round whose data has gone succeeds (the answer needs no round data); only reading it is a 410.
- `/api/countries`, `/api/rivers` and `/api/lakes` are cached.

## Persistence

- H2 in memory (PostgreSQL mode) by default, so games are lost on restart; Postgres under `prod`. Flyway owns the schema (`src/main/resources/db/migration`, `ddl-auto=validate`), and the same migrations run on H2 in every test. Any entity change needs a new `V<n>__...sql` migration, never an edit to an applied one.
- `game_entity.difficulty` (`EASY`, `NORMAL` or `HARD`, by name) is a nullable column, set when the game is created and never updated (`@Column(updatable = false)`). `NULL` means unknown (a game from before the column, or a client that sent neither `difficulty` nor `hardMode`); `GameEntity.difficulty()` reads it as `NORMAL` for the rules and the API, and `getDifficulty()` keeps the `NULL` for statistics. `Difficulty.resolve(difficulty, hardMode)` turns a request into it. `game_entity.hard_mode` is kept, and written from the difficulty (`true` for `HARD`, `false` for the others, `NULL` for unknown), because the previous version of the app still reads and writes it during a deploy; a later cleanup drops it. **Every rule check uses the game's effective limits**: `RoundRules` and `GameResults` take the game's `Difficulty`, and the plain `GameType.guessLimit()` / `hintCount()` are the Normal values, for the daily picker and stats lookups only. `RoundContinents` (a `@Component`) works out the continents of an Easy round from its `GameData`; `GameData` isn't sealed, so a new round type is caught by `GameApiIT`, which plays an Easy game of every type, rather than by the compiler.
- `game_entity.daily_date` is a nullable date, set when a daily game is created and never updated (`@Column(updatable = false)`); it is the challenge's date, not when it was played, and is never in an API response.
- `GameEntity.publicId` (random UUID) is the id in URLs; the `long` key never leaves the server. `created_at` is rounded down to the hour.
- `GameCleanupService` deletes each game `geogames.games.max-age` (24 h) after it is created with one bulk delete (the rounds go through the foreign key's `on delete cascade`, not JPA), so it is safe for every instance to run it. It runs at start-up and then every `geogames.games.cleanup-interval` (1 h). The free Render service rarely stays up an hour, so the start-up run usually does the work.
- `game_round_guess` (`round_id`, `position`, `guess`, `correct`; an element collection of `GameRoundEntity`) holds a round's guesses in order. It has `on delete cascade` to the round, so `GameCleanupService`'s bulk delete removes them. Changing it bumps the round's version.
- `game_round_hint` (`round_id`, `hint_index`, `guesses_before`; an element collection of `GameRoundEntity`) holds the hints taken before the answer, with `on delete cascade` like the guesses. `hints_used` is still set only when the round is answered.
- `GameRoundEntity` has a `version` column for optimistic locking, so two writers of one round can't both succeed.
- Each `GameRoundEntity` stores only a short `roundKey` (such as `country:France`, `river:Q46841` or `tripoint:A|B|C@lat,lon`), not the round's data: the geometry is already in the jar and cached by the loaders, and storing it made a 10-round game about 0.5 MB of heap. `GameService` rebuilds the round with its type's generator (`RoundGenerators.rebuild`, which calls `RoundGenerator.rebuild(roundKey)`) and serialises it into `GameRound.jsonBlob` on every read. Answering does not rebuild the round: `submitAnswer` returns a `RoundAnswerResponse` (answer state, hints, points and the `GameResult`). A renamed country keeps its old name as an alias, and `StoredRoundKeys` (through `RoundRules.currentRoundKey`) uses that to bring a stored key up to date before the rebuild, so games in progress and pinned daily challenges survive a rename. A key whose data has gone (a deploy removed a river or a country) throws `RoundDataMissingException`, which `ApiExceptionHandler` turns into a 410 with a `ProblemDetail`. Don't cache the rebuilt JSON: it would bring back the heap this avoids.

## Usage statistics

`GameService.submitAnswer` publishes a `RoundAnswered` event on the first answer to a round (not on a repeat or a 409). `service/stats/RoundStatsRecorder` handles it after the answer's transaction commits, on the one-thread `statsExecutor` (`config/StatsConfig`, queue of 1000), and `RoundStatsStore` splits the flat `RoundResult` across a small star schema with `JdbcClient`, in the same database as the games: one `stat_round` row per answered round, one `stat_game` row per game, and lookup tables (`stat_game_mode`, `stat_game_type` with its hint count and guess limit, `stat_answer_state`, `stat_round_key`). `round_result` is a read-only view that joins them back to the flat columns; write through `RoundStatsStore`. The lookup rows are created on first use and cached by id, so they are never deleted or updated, and tests never clean them. `stat_round` is kept at 8 fixed-width columns on purpose. There is one stats thread per instance; a lost race on a lookup or game row re-reads the winner's row, so `RoundStatsStore` must stay non-transactional for that to work on Postgres. A failure or a full queue only logs a WARN and drops the row, so stats never break or slow an answer. The `stat_*` tables are created by Flyway migrations, have no foreign keys to the game tables and are never deleted by `GameCleanupService`.

Anonymity rules: never store an IP, a header, either game id, a timestamp (only the UTC date) or anything from the browser, and never expose or log `GameEntity.playId` (the random id that links the rounds of one game, not the `publicId`). `wrong_guesses` is `NULL` when the client didn't report it; don't turn that into 0. `stat_game.hard_mode` and `stat_game.difficulty` (both also in `round_result`) are the settings the player chose for the game (Hard mode, and `EASY`, `NORMAL` or `HARD`), `NULL` when unknown; they are game settings, not browser data, so they are allowed, but don't turn `NULL` into `false` or `NORMAL`. `RoundStatsStore` wraps both in a `SqlParameterValue` because `Map.of` rejects null. `RoundStatsRecorder` records the game's effective `hint_count` and `guess_limit`, so an Easy round gets its own `stat_game_type` row: the row describes the rules the round was played under. `geogames.stats.enabled=false` turns recording off. A new `GameType` needs nothing extra for stats.

## Game types

`GameType` is persisted with `@Enumerated(EnumType.STRING)` and sent to clients as `api/GameTypeResponse` (`{name, answerCount, hintCount, guessLimit}`), so the JSON shape doesn't depend on the enum. `RANDOM` is a request-only value, parsed by `service/GameSelection`, and is not a `GameType`.

Adding a type (the root `CLAUDE.md` has the four steps):
- **The `GameData` record** in `model/`: `gameType()` returns the constant, `subjectId()` says what the round is about, and `roundKey()` (defaults to `subjectId()`) is what is stored. The key must be unique within the type, so override it as `Tripoint` does when `subjectId()` isn't.
- **The generator** implements `service/RoundGenerator`: a `@Service`, or a `@Bean` in a `@Configuration` when several types share one class. `RoundGenerators` fails start-up with an `IllegalStateException` if a `GameType` has no generator, or has two. `generate` takes the `Random` to pick with (use `helper/RandomPicker`): `GameService` passes the shared bean (`config/RandomConfig`), a daily challenge a seeded one, and tests a seeded one.
  - A generator whose round is about one item (a country, a river, a lake) extends `service/SubjectRoundGenerator`: it supplies `candidates()`, `id`, `find(id)` and `toRound`, and the shared `generate` and `rebuild` apply the prefix from `model/SubjectIds`, the exclusions and the single `RandomPicker.pickDistinct` call. Keep that call and the candidate order as they are: a daily challenge is seeded, so changing either changes which rounds it picks. Pairs and tripoints implement `RoundGenerator` directly.
  - `generate(count, excludedSubjects, random)` must not return a round whose `subjectId` is excluded. `RoundGenerators.generateMixed` passes the subjects already used in a `RANDOM` game, so a mixed game never asks about the same tripoint or river twice (a river by shape and the same river on the map).
  - `rebuild(roundKey)` must build the round with the same private method `generate` uses (so the two can't drift), must not apply the eligibility filter, and throws `RoundDataMissingException` for a key with no data. `RoundRebuildIT` checks every generator against all the real data automatically.

## Game families

**Tripoints.** `TripointRoundGenerator` picks random definitions from `processed/tripoints.json` and builds each country with `CountryShapeService.loadDisplayCountry(name)`, so `jsonBlob` carries the simplified `processed/country-shapes` outline (in the usual `Country` shape), not the full-resolution geometry of `processed/countries`.

**Rivers.** Two types share the 50 rivers in `processed/rivers` (read by classpath glob, cached as `rivers`): `RIVERS_BY_SHAPE` (the line on a blank map), and `RIVERS_BY_COUNTRIES` (the outlines of the countries it flows through; only rivers through three or more). `model/River` is the file format and `model/RiverRound` (`gameType`, `river`, `countries`) the round data. `service/RiverRoundGenerator` is one class, registered as two beans in `config/RiverGamesConfig`, each with an eligibility filter and a function that attaches countries. To remove a variant, delete its `GameType` constant, its `@Bean`, and its frontend module, registry entry and map pair.

**Lakes.** `LAKES_BY_SHAPE` (`answerCount` 1, `hintCount` 3, `guessLimit` 5). `model/Lake` is the file format in `processed/lakes` and `model/LakeRound` (`gameType`, `lake`) the round data; its subject id is `lake:<QID>`. `service/LakeLoaderService` reads the files (cached as `lakes`, plus `lakeNames` for `GET /api/lakes`), and `service/LakeRoundGenerator` is a plain `@Service`.

**Pair games.** `BORDERS_BY_SHAPE` ("Border Shapes": the border between two countries as a lone line) and `MERGED_COUNTRIES` (two neighbours filled as one shape), both `answerCount` 2. `model/CountryPairRound` (`gameType`, the two `countries` sorted by name, `sharedBorder`, `borderKm`, `neighbours`, `focus`, `borderBounds`) holds references to the cached `CountryShape`s, and its subject id is `pair:<A>|<B>` with the names sorted (shared by both types, so a mixed game never shows a pair twice). The shared border is picked out of the first country's `landBorders` with `CountryShape.Neighbour.lines` (the line indexes for each neighbour, written by `CountryShapeBuilder`); `CountryShape.areaKm2` is the area of the largest part. `service/CountryPairRoundGenerator` is one class registered as two beans in `config/CountryPairGamesConfig`; it lists the pairs from the cached shapes and builds nothing until a pair is picked. The eligibility rules, with reasons, are in `helper/CountryPairEligibility` (each a mainland neighbour of the other and a border of at least 50 km; Merged Countries also needs the areas within a factor of 8).

**Cities.** `COUNTRIES_BY_CITIES` (`answerCount` 1). `processed/cities.json` (one file, from `CityLoaderMain`) is read once by `service/CityService` into records of primitives (`model/City`, `model/CountryCities`), well under a megabyte. `model/CountryCitiesRound` (`gameType`, `country`, `cities`) has the subject id `country:<name>`; `service/CountryCitiesRoundGenerator` is a plain `@Service` and the threshold (at least 8 cities) is in `helper/CountryCitiesEligibility`.

**Country rivers.** `COUNTRIES_BY_RIVERS` (`answerCount` 1). `processed/country-rivers/` has one file per country (`model/CountryRivers`: major and minor rivers clipped at the borders, and the lakes on the shore) and `index.json` (`model/CountryRiversIndexEntry`: river count, km and lake count). `service/CountryRiversService` keeps only the index in memory; `load(name)` reads that country's file every time and has no cache **on purpose**: the geometry is the one large new data set (about 1.6 MB of JSON, about four times that as boxed lists). Don't add `@Cacheable` to it. `service/CountryRiversRoundGenerator` filters the index (`helper/CountryRiversEligibility`: at least 5 rivers and 1,000 km) so it reads no geometry until a country is picked, and the round (`model/CountryRiversRound`, subject id `country:<name>`) is built from the file and the cached shape.

**Country shapes.** Three types use `processed/country-shapes`: `COUNTRIES_BY_NEIGHBOURS` ("Country Gaps": the neighbours' filled outlines, the country is the gap), `COUNTRIES_BY_COASTLINE` (only the coast, as lines) and `COUNTRIES_BY_LAND_BORDERS` (only the land borders, as lines). `model/CountryShape` is the file format (including `continents`, one or two continent names) and `model/CountryShapeRound` (`gameType`, `country`, `neighbours` as `CountryOutline`s) the round data; its subject id is `country:<name>`, shared by all three. `service/CountryShapeRoundGenerator` is one class, registered as three beans in `config/CountryGamesConfig`, with the eligibility thresholds (and the reason for each) in `helper/CountryShapeEligibility`. Removing a variant works as for rivers. `GET /api/countries` (`CountryNameService`) is built from these shapes, so the app never reads `processed/countries` (it is loader and test input only); Antarctica has no shape and so is not in the autocomplete list.

## Daily challenge

`POST /api/daily-games` (`DailyChallengeService`) makes a game from a date's five pinned rounds, one game per call, so answers stay per player. `DailyRoundPicker` picks them from a seed (SHA-256 of the date): five different game types that aren't `GameType.extraDifficult()` (keep that list in step with `extraDifficult: true` on the frontend modules; both sides have a test) and five different subjects.

- **Pinning.** The first request for a date stores its rounds in `daily_challenge` (`DailyChallengeStore`, deliberately not `@Transactional`, a lost insert race is a `DuplicateKeyException` and then reads the winner's row). Later requests copy the stored rows, so a deploy mid-day can't change the puzzle. The seed alone would not give that.
- **Date range.** The client sends its local date. The server accepts it within one day of its own UTC date (every time zone) and not before `DAILY_EPOCH` (the date of Daily #1; `number` is days since it plus one). Anything else, or a malformed date, is a 400. With no date the server uses its UTC date (`Clock` bean in `config/ClockConfig`).
- **Mending a day.** The service doesn't check that pinned keys still rebuild. If a deploy removes the data behind one, that round is a 410. Delete the day's row (`delete from daily_challenge where challenge_date = '...'`) and the next request generates it again. The day's totals (`daily_score_by_difficulty`) are kept.
- **Daily scores.** `daily_score_by_difficulty` has one row per challenge date and difficulty (a league: `EASY`, `NORMAL` or `HARD`; a game of unknown difficulty counts as `NORMAL`) with running counters (`players`, `score_total`, `bucket_0`..`bucket_10`): about 90 bytes a league a day, no per-player rows, so nothing to clean up, and `GameCleanupService` never touches it. It is separate from `daily_challenge` so that mending a day doesn't wipe it. `game_entity.daily_date` (null for non-daily games, set at creation, never updated) says which day a game belongs to. `GameService.answer` counts a daily game once, in the answer's own transaction (so a rollback rolls the count back), when its last unanswered round gets its first answer, whatever the `AnswerState`; `DailyScoreStore.recordFinished` adds the score to the bucket `min(10, score * 10 / maxScore)`. A repeated answer is a no-op, so it never counts twice; a failed update only logs the date. Known gap: two final answers at the same moment may both see the other round as unanswered and the game isn't counted; don't add locking for it. `DailyScoreStore.ensureDay` (non-transactional, like `DailyChallengeStore`) makes the game's league row when a daily game is created. `GET /api/daily-scores/{date}?difficulty=` (`DailyChallengeService.score`) reads one league's row (default `NORMAL`), uncached, and allows past dates back to Daily #1. Each player is compared only with players on the same difficulty. The old `daily_score` table was never split by difficulty: V15 copied its rows into the `NORMAL` league and left it in place, unused, because the previous version of the app still writes it during a deploy; a later cleanup drops it. The `daily_score_history` view (now over the new table, with `difficulty`) adds `average_score` for the owner in the database console; there is no public history.
